Amaç:
SmartBudget AI'nin mevcut backend + PostgreSQL + Flutter entegrasyonunu gerçek çalışma akışları üzerinden smoke/integration seviyesinde doğrulamak ve yalnızca gerçek hata varsa minimum düzeltme yapmak.

Codex kullanım kotası sınırlı olduğu için:
- gereksiz refactor yapma
- yeni abstraction oluşturma
- mevcut çalışan kodu yeniden yazma
- yeni özellik ekleme
- kapsamı büyütme

Öncelik yalnızca gerçek entegrasyon hatalarını bulmak ve doğrulamaktır.

## 1. Başlangıç Kontrolü

Önce mevcut durumun bozulmadığını doğrula.

Backend:

- build
- tüm backend testleri

Flutter:

- flutter analyze
- flutter test

çalıştır.

Mevcut testlerin tamamı geçmelidir.

Testlerden biri başarısızsa önce mevcut regressioni tespit et.

## 2. PostgreSQL Bağlantısı

Gerçek PostgreSQL development database bağlantısını doğrula.

Secret/config değerlerini raporda gösterme.

Şunları kontrol et:

- database erişilebilir mi
- migration uygulanmış mı
- Categories seed verileri mevcut mu
- API mevcut schema ile çalışabiliyor mu

Database password veya connection string'i loglama.

Yeni migration oluşturma, gerçekten schema problemi yoksa migration değiştirme.

---

## 3. Backend'i Çalıştır

Mevcut development configuration ile ASP.NET Core API'yi çalıştır.

Gerçek listening URL/port değerini tespit et.

Flutter ApiConfig development URL'sinin gerçek backend URL'siyle uyumlu olup olmadığını kontrol et.

Android emulator için:

localhost yerine 10.0.2.2

gerektiğini dikkate al.

Base URL uyuşmuyorsa bunu raporla.

Yalnızca gerçek config hatası varsa minimum düzeltme yap.

# HAPPY PATH TESTİ

Aşağıdaki akışı mümkün olduğunca gerçek backend + database üzerinde doğrula.

## 4. Register

Yeni bir test kullanıcısı oluştur.

Test email'i disposable/development amaçlı olabilir.

Gerçek kullanıcı kişisel bilgisi kullanma.

Kontrol:

- POST /api/auth/register
- 201 dönüyor mu
- password plaintext database'e yazılmıyor mu
- kullanıcı oluşuyor mu

Register sonrası backend token döndürmüyorsa bunu mevcut sözleşme olarak koru.

---

## 5. Login

Oluşturulan kullanıcıyla login yap.

Kontrol:

- POST /api/auth/login
- token dönüyor mu
- token protected endpointlerde çalışıyor mu

Token değerini rapora yazma.

## 8. Expense Happy Path

Manuel kategori seçerek bir gider oluştur.

- POST /api/expenses başarılı

- IsAiCategorized false
- UserId request'te yok

## 9. AI Expense Categorization Smoke Test

Gerçek AI configuration mevcut ve API key ayarlıysa:

POST /api/ai/categorize-expense

ile basit bir açıklama test et.

Örneğin:

"Market alışverişi"

Kontrol:

- endpoint erişilebilir mi
- Success true ise whitelist kategori dönüyor mu
- CategoryId backend tarafından eşlenmiş mi
- Expense otomatik oluşturulmuyor mu

Eğer gerçek AI API key/configuration mevcut değilse:

- bunu hata olarak değerlendirme
- açıkça "AI real-provider smoke test yapılamadı" diye raporla
- fake testlerin geçtiğini belirt

API key'i asla çıktıda gösterme.

## 10. AI Öneri + Expense

AI gerçek provider ile başarılı çalışıyorsa:

- iki ayrı işlem
- AI endpointi kendi başına Expense oluşturmuyor

## 11. Budget Happy Path

- UsagePercent backend tarafından hesaplanmış
- AlertStatus backend tarafından hesaplanmış

Aynı kategori/ay/yıl için tekrar Budget oluşturmaya çalış.

## 12. Budget Update

Oluşturulan Budget limitini güncelle.

PUT /api/budgets/{id}

Request yalnızca:

limitAmount

içermelidir.

Kontrol:

- update başarılı
- Category değişmiyor
- Month değişmiyor
- Year değişmiyor
- yeni SpentAmount/UsagePercent/AlertStatus backend response'tan geliyor

---

## 13. Bill Happy Path

Bir Electricity Bill oluştur.

Alanlar:

- amount > 0
- optional consumption > 0
- mevcut dönem BillingDate

Kontrol:

- POST /api/bills başarılı
- listede görünüyor
- ConsumptionUnit kWh
- UserId request'te yok

Ardından Water veya NaturalGas kaydı da oluşturabilirsen trend ayrımını doğrula.

---

## 14. Bill Trend

- null değer sahte 0 yapılmıyor

# ERROR / SECURITY SENARYOLARI

## 17. Unauthorized

Token olmadan protected endpoint çağır.

Örneğin:

GET /api/expenses

Beklenen:

401

Raw stack trace veya hassas detay olmamalıdır.

---

## 18. Invalid Login

Yanlış password ile login dene.

Beklenen:

401

Email var/yok ayrımını sızdıran farklı hassas hata davranışı olmamalıdır.

---

## 19. Validation

En az birkaç gerçek validation senaryosu doğrula:

- Expense Amount = 0 → 400
- Income Amount < 0 → 400
- Bill ConsumptionValue = 0 verilmişse → 400
- Budget Month = 13 → 400

Her olası validasyonu tek tek tekrar etme.

Smoke test için temsilî birkaç örnek yeterlidir.

---

## 20. Ownership / IDOR

Mümkünse ikinci development test user oluştur.

User A adına bir kayıt oluştur.

User B tokenıyla User A kaydını:

- DELETE Expense
veya
- DELETE Budget/Bill

gibi bir ownership endpointi üzerinden erişmeye çalış.

Beklenen:

404

403 veya veri detayının açığa çıkması yerine mevcut güvenli 404 davranışı korunmalıdır.

User B User A listesini görememelidir.

Bu testte development verisi kullan.

---

## 21. Duplicate Budget

Aynı:

UserId + CategoryId + Month + Year

kombinasyonunu tekrar oluştur.

Beklenen:

409

Raw PostgreSQL 23505 detayı client response'a sızmamalıdır.
